## Context

当前 `internal/tdx.Service` 在构造时只创建客户端对象，连接由部分 gotdx 高阶方法按需建立；公告、财务等底层方法直接执行协议，首次调用会因连接为空失败。`Ready()` 仅检查客户端组是否存在，无法区分未连接、连接正常或断线状态。动机和可观察要求分别见 `proposal.md` 与三个 delta specs。

主市场与 MAC 使用不同连接和握手方式，单个协议连接仍需串行使用。HTTP 请求有自身期限，启动连接、请求前恢复、业务调用和重试都必须有界；优雅关闭后不得再启动连接恢复。

## Goals / Non-Goals

**Goals:**

- 为每个客户端组分别维护主市场和 MAC 的真实连接状态及所有权。
- 在 HTTP 监听前完成全部客户端组的两类初始连接，失败时安全清理已建立资源。
- 在每次协议调用前以并发安全方式确认对应连接，并在网络错误后清除状态、重连和重试。
- 使 `/health/ready` 反映全部必需连接是否真实可用。
- 保持现有路由、DTO、错误码、客户端池并发边界和配置项兼容。

**Non-Goals:**

- 不新增无限循环的后台重连器、连接保活协议或新的公共运维接口。
- 不保证第三方 TDX 节点持续可用，也不重试业务校验错误或已确认获得有效响应的调用。
- 不修改 gotdx 源码，不增加数据库、缓存或跨进程连接协调。

## Decisions

### 使用同步启动连接并让构造函数返回错误

将服务初始化从仅分配对象改为“创建全部客户端组并连接主市场与 MAC”。`tdx.New` 返回 `(*Service, error)`；`cmd/api` 只有在初始化成功后才创建并启动 HTTP Server。若任一连接失败，初始化过程关闭此前已创建的全部连接并返回带上下文错误。

备选方案是先监听 HTTP，再通过后台任务连接并让 readiness 暂时失败。该方案允许进程启动，但不满足“启动的时候就连接”和启动失败明确可见的要求，并会增加启动状态机复杂度。

### 在客户端组内维护独立连接状态

每个池项为主市场和 MAC 分别保存连接可用状态。状态只在持有该池项互斥锁时读写：连接成功后设为可用；协议网络错误或断开后先清除状态，再关闭连接；重连成功后恢复状态。服务级 readiness 汇总全部池项的两类状态，并使用独立同步保护，避免健康检查读取数据时产生竞态。

不使用 `CurrentAddress()` 作为连接状态，因为它表示配置或最近使用的地址，不证明 socket 当前可用。也不在每次请求发送额外心跳，因为这会使所有业务调用增加一次网络往返，并且部分协议没有统一心跳语义。

### 请求前检查与现有重试合并为一个有界流程

请求从池中取得客户端组并加锁后，根据 operation 前缀选择主市场或 MAC：若状态不可用则先执行对应连接；随后调用业务协议。可重试网络错误使状态失效并断开对应连接，下一次重试先重连后再执行原业务调用。主市场错误不得断开健康的 MAC 连接，反之亦然。

备选方案是在每次错误时同时断开两个客户端。该方案实现较短，但会让单一上游故障扩大为两套协议同时抖动，并使 readiness 和连接状态不准确。

### 不运行常驻后台重连循环

自动连接由两个触发点完成：启动阶段，以及请求发现断线或协议调用发生可重试错误时。这样能满足断线自动恢复和请求前检查，同时保持重试次数、上下文期限和关闭行为可控。没有流量时，断线不会产生持续探测负载；readiness 在状态失效后保持失败，直到请求触发恢复或服务重启。

备选方案是每个连接运行后台指数退避重连 goroutine。它能在无流量时恢复 readiness，但需要额外配置、时钟测试、关闭协调和防止重连风暴；当前需求不要求无请求自动恢复，因此不采用。

### 关闭状态阻止新的连接

Service 使用关闭标志和一次性关闭语义。关闭开始后，新的 `Call` 和连接恢复返回明确错误；关闭流程等待已取得池项的调用归还后，再逐一断开连接。这样避免关闭期间 goroutine 刚断开连接又被请求重新建立。

### 测试使用可替换的连接适配边界

将连接、断开和协议调用封装为小型内部接口或函数依赖，使单元测试无需真实 TDX 网络即可覆盖启动部分失败清理、首次底层调用、断线重连、重试上限、协议隔离、并发和关闭。显式启用的集成测试继续验证真实主市场公告、财务和 MAC 首次连接。

### 仅记录连接生命周期状态变化

`internal/tdx` 使用注入的 `slog.Logger` 记录启动连接、请求触发重连、连接成功、连接失败、网络错误断开和服务关闭。字段统一包含 `protocol`、`client_group`、`trigger`，真实客户端可额外记录 `address`；错误事件包含 `error`。健康连接上的普通请求不产生日志，避免高频行情调用淹没生命周期事件。日志不得包含 `Params`、证券数组或上游响应。

默认使用 `slog.Default()`，测试注入内存 handler 验证事件和字段。相比在 HTTP 层记录上游错误，适配器层能准确区分主市场和 MAC、连接与业务协议阶段，并覆盖启动时尚未存在 HTTP 请求的事件。

## Risks / Trade-offs

- [启动依赖第三方节点，短暂网络故障会导致进程退出] → 使用配置的主机池和有界故障转移，并由 Compose 重启策略再次尝试；错误日志包含协议类别和根因。
- [每个池项都在启动时建立两条连接，较大池会增加启动时间和上游连接数] → 保持现有池大小上限，按顺序或受控并发初始化，并受统一启动期限约束。
- [socket 可能在 readiness 检查后立即断开] → readiness 只表达最近确认状态；业务请求仍在调用前检查，并在网络错误后自动恢复。
- [gotdx 没有公开精确 socket 状态] → 状态由成功连接和协议错误驱动，不从地址字段推断；真实可用性最终由下一次协议操作确认。
- [重试可能重复只读请求] → 仅对当前已定义的只读 API 和明确可重试的连接错误执行，并维持现有重试上限。
- [多客户端组启动可能产生较多日志] → 仅记录状态变化并保留 `client_group` 便于聚合，不记录健康请求。

## Migration Plan

1. 引入可测试的连接适配边界和独立主市场/MAC 状态，不改变路由。
2. 修改服务初始化和 `cmd/api` 装配，使监听前连接并传播启动错误。
3. 将请求前检查、按协议断开和重连纳入现有有界重试流程。
4. 更新 readiness、单元测试、竞态测试、真实集成测试和部署文档。
5. 发布后观察启动失败率、上游错误分类和容器健康状态。

回滚时恢复上一版本镜像；本变更不涉及持久化数据或 API 数据迁移。
