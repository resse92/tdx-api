## Why

部分 `gotdx` 底层方法不会自动建立连接，导致公告、财务等接口在进程启动后的首次请求中返回 `connection is nil`；现有就绪检查也只判断客户端对象是否存在，无法反映真实上游连接状态。服务需要明确管理主市场与 MAC 连接，避免连接状态取决于接口调用顺序。

## What Changes

- 应用启动时主动连接主市场与 MAC 上游，连接失败时阻止服务进入就绪状态并返回明确启动错误。
- 持续跟踪两类客户端的实际连接状态，连接断开后自动执行有界重连和主机故障转移。
- 每次接口请求调用对应协议能力前检查连接；未连接时先同步尝试恢复，成功后执行请求，失败则返回标准上游错误。
- 就绪检查基于主市场与 MAC 的真实连接状态，而不是客户端对象是否已创建。
- 使用结构化日志记录主市场与 MAC 的连接尝试、成功、失败、断线、重连和关闭状态变化。
- 增加首次调用底层协议、断线恢复、并发请求、关闭期间停止重连及真实上游连接的测试。
- 公共业务路由和请求 DTO 不变；CORS、能力覆盖范围和容器部署方式不变。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `main-market-http-api`：强化主市场客户端的启动连接、断线自动重连、请求前连接检查和就绪状态要求。
- `mac-market-http-api`：强化 MAC 客户端的启动连接、断线自动重连、请求前连接检查和就绪状态要求。
- `containerized-service`：要求容器就绪状态反映两类 TDX 上游的真实连接状态。

## Impact

- 主要影响 `cmd/api` 的启动流程、`internal/tdx` 的连接状态机、结构化日志与重试逻辑、`internal/httpapi` 的就绪检查，以及相关配置和测试。
- 启动过程将产生真实 TDX TCP 连接；上游不可达时服务不会错误报告为就绪。
- API 路径、请求参数和成功响应契约不变；连接失败仍使用既有 `UPSTREAM_UNAVAILABLE` 或 `UPSTREAM_TIMEOUT` 错误。
- 不新增依赖，不扩大 gotdx 能力范围，不改变 CORS 或 Docker 镜像结构。
