## Context

当前 `internal/httpapi` 将所有稳定路由直接映射到 `tdx.Caller`，`internal/tdx` 持有并发隔离的主市场和 MAC 连接池。板块列表与成分没有领域存储，进程也没有后台任务生命周期。参见 `proposal.md` 的动机和 `specs/` 中的行为边界。

该变更横跨配置、持久化、上游编排、HTTP 路由和进程关闭，并引入 SQLite 驱动与数据模型。现有 HTTP 参数及响应 JSON 必须保持兼容，真实 TDX 网络不能成为确定性测试前提。

## Goals / Non-Goals

**Goals:**

- 建立可独立测试的板块仓储和刷新服务，并保持 `httpapi -> boardcache -> tdx` 的单向依赖。
- 保证全量刷新原子发布、按资源缺失回源和同键请求合并。
- 将调度器、HTTP 服务、SQLite 和 TDX 连接纳入同一优雅关闭期限。
- 让 SQLite 文件在非 root 容器中可写并可通过卷持久化。

**Non-Goals:**

- 不缓存板块成分实时行情 `/api/v1/mac/boards/quotes`。
- 不增加手动刷新、缓存清除、更新时间查询等公共 HTTP 接口。
- 不引入过期时间；存在的数据一直可读，直到一次完整刷新成功替换。
- 不实现多实例间的分布式调度或请求合并；每个服务实例独立维护其 SQLite 和调度状态。

## Decisions

### 使用独立 `internal/boardcache` 领域服务

新增包持有 `Repository` 和最小化的上游 `Fetcher` 接口，提供板块列表/成分的缓存优先读取、全量刷新、调度启动和关闭。HTTP 处理器只将两个板块读取操作委托给该服务，其他操作仍直接使用 `tdx.Caller`。后台刷新复用现有 `tdx.Service` 连接池，不创建或拥有额外 gotdx 连接。

备选方案是在 `httpapi` 或 `tdx.Service.Call` 中嵌入缓存判断。前者会把后台生命周期和持久化泄漏到传输层，后者会让协议适配器同时承担缓存策略，因此不采用。

### 使用 SQLite 关系表和代际发布

使用纯 Go SQLite 驱动，避免最终镜像引入 CGO 运行时依赖。仓储维护板块、成分和元数据表；板块及成分以稳定业务键去重，并保存足以重建现有 JSON 响应的字段。全量刷新先在同一事务中写入新 generation，所有板块成分获取成功后切换 active generation 并清理旧 generation。普通缺失回源只原子替换对应资源，不切换全局 generation。

相比将整个上游响应保存为单个 JSON blob，关系记录可以稳定执行 `limit`、检测指定板块是否无记录，并避免每次读取解码全部板块。相比内存缓存，SQLite 能跨重启并支持容器卷持久化。

迁移通过幂等建表和 `schema_version` 元数据完成。首版只有新库，无历史数据转换。

### 固定北京时间日程并显式计算下一触发点

调度器加载 `Asia/Shanghai`，按当地日期计算下一次 09:00、15:00、20:00，而不是使用进程本地时区或固定 UTC 偏移。一个互斥状态保证同一实例最多一个全量刷新；若触发时仍在运行则记录并跳过，不积压任务。

相比引入 cron 库，三个固定时间点用标准库计时器即可清晰处理时区和关闭，减少依赖。启动时不自动全量预热，严格遵循仅定时刷新或请求缺失回源的语义。

### 全量抓取与发布边界

一次周期先按允许的最大协议数量抓取板块列表，再逐个抓取每个板块的完整成分。抓取采用小型、有界并发，复用 `tdx.Service` 的连接池且不超过池容量；周期使用独立的刷新超时配置。任一抓取失败即丢弃暂存 generation，已有 active generation 不变。

对 HTTP 缺失回源，以资源键进行 singleflight 合并。等待者继续服从各自请求上下文；发起的共享抓取使用有界内部上下文，避免首个客户端取消导致所有等待者必然失败。上游返回成功但空集合时记录一个已加载标记，从而区分“有效空结果”和“尚未加载”，避免反复回源。

### 配置、启动和关闭顺序

`internal/config` 新增 SQLite 文件路径和刷新超时，提供适用于容器的默认数据路径并执行非空、正时长校验。`cmd/api` 依次创建 TDX 服务、打开并迁移 SQLite、创建板块缓存服务、启动调度器，最后监听 HTTP；任一步失败均逆序释放已创建资源。

关闭时先停止 HTTP 接收，再停止调度器并等待/取消刷新，随后关闭 SQLite，最后关闭 TDX 连接。所有等待均受现有 `SHUTDOWN_TIMEOUT` 限制。存活检查不依赖缓存内容；SQLite 初始化是启动门槛，但板块数据为空不影响 TDX 就绪语义。

Compose 为数据库目录声明持久化卷并保证非 root 用户可写。OpenAPI 的路径、参数、响应及 CORS 配置均不变化，只更新接口说明以标明缓存语义。

## Risks / Trade-offs

- [全量板块成分刷新耗时并占用连接池] -> 使用不超过池大小的有界并发、独立刷新超时和跳过重叠周期；HTTP 请求仍通过现有池公平等待并受请求超时保护。
- [gotdx 返回结构变化导致持久化映射失配] -> 在适配边界显式转换领域记录，以编译期类型和固定响应契约测试覆盖映射。
- [SQLite 文件增长或残留暂存 generation] -> 成功发布后事务内清理旧代；启动迁移后清理非 active 的未完成代，并启用 WAL 与合理 busy timeout。
- [多实例共享同一 SQLite 卷造成调度竞争] -> 首版明确要求每实例独占 SQLite 文件；多实例共享缓存和领导者选举不在本变更范围。
- [缓存数据长期陈旧] -> 规格选择可用性优先，失败保留旧数据并通过结构化日志暴露刷新时间、阶段和错误，后续可基于运维需求增加指标或陈旧度策略。

## Migration Plan

1. 发布包含新配置和幂等 SQLite 迁移的版本，并为容器挂载独占、可写的持久化目录。
2. 应用首次启动创建空库；在下一个计划时间全量填充，计划时间前的 HTTP 请求按资源缺失回源。
3. 观察三个刷新时点的开始、成功、失败、耗时和跳过日志，并确认缓存命中不产生对应 MAC 调用。
4. 回滚时先停止服务，再部署旧版本；旧版本忽略 SQLite 文件和新增配置。保留卷以便重新升级，或在确认无需恢复后离线删除。
