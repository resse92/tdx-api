## 背景

当前仓库仅包含 OpenSpec 配置。新服务需要建立 Go 项目结构，并在无状态 HTTP 接口之后集成面向 TCP、具有连接状态的 `gotdx` 客户端。服务仅使用沪深主市场和 MAC 主市场连接。`gotdx` 当前要求 Go 1.26 或更高版本，并提供主机池、超时配置、高阶与底层调用方法。变更动机参见 `proposal.md`，外部契约参见 delta specs。

即使上游节点失败或 `gotdx` 返回类型发生变化，公共 API 仍需保持稳定。HTTP 请求可能并发到达，而单个协议连接可能需要串行访问，或在网络错误后进行替换。容器还必须能够访问 TDX TCP 和 HTTP 上游主机。

## 目标与非目标

**目标：**

- 使 HTTP 路由、参数校验、上游编排和传输层可以独立测试。
- 使用明确路由和强类型请求模型覆盖规格中确定的全部稳定股票相关能力。
- 集中管理配置、错误、响应格式、CORS、生命周期和 OpenAPI 元数据。
- 通过同一个容器镜像实现可重复的本地及生产式启动流程。

**非目标：**

- 首版稳定 API 不代理仅商品使用的 `Goods*`、ICFQS 原始接口、实验性方法或兼容性方法。
- 不使用数据库持久化或缓存行情数据。
- 本变更不增加身份认证、权限控制、计费或按调用方限流。
- 除有界故障转移和透明错误外，不保证第三方 TDX 节点的可用性或数据正确性。

## 技术决策

### 按传输层、领域服务和上游适配器组织应用

使用 `cmd/api` 负责进程启动，`internal/config` 负责环境变量解析，`internal/httpapi` 负责 Gin 路由和中间件，`internal/tdx` 负责持有 `gotdx` 客户端的适配器。处理器依赖小型服务接口而非具体客户端，以支持确定性的单元测试。

备选方案：将全部处理器和 `gotdx` 调用放入 `main`。该方案初期更短，但面对大量接口时难以管理生命周期、复用校验逻辑和测试错误行为。

### 使用明确的资源路由而不是任意方法调用

在 `/api/v1` 下按 `stocks` 和 `mac` 对路由分组，并为规格中的各业务能力类别提供明确处理器。请求 DTO 只接受业务语义字段，将 `period`、`adjust`、`offset/limit` 和 `symbols` 转换为 `gotdx` 所需协议参数。按证券查询统一接收 `000001.SZ`、`600519.SH` 格式的 `code`，在 HTTP 边界将后缀转换为 `gotdx` 所需的 `market` 和纯 6 位代码；批量项同样只接收 `code`。板块成分和行情使用固定路径，并通过 `board_symbol` 查询参数接收板块代码。仅无 `code` 的全市场接口保留 `market`。每个路由使用独立参数白名单，未知 query 字段和 JSON 字段均被拒绝。协议分页起点、倍率、位图、排序、过滤和服务信息不注册公共参数或路由。原始文件访问不注册公共路由，仅在服务器内部按需使用。文档和测试中维护路由到 `gotdx` 的能力覆盖矩阵，使新增能力可审计。

公共前缀按上游协议客户端划分，而不是按证券子类型划分：普通主市场客户端的股票、指数、公告和 F10 能力全部归入 `/api/v1/stocks`；MAC 客户端能力全部归入 `/api/v1/mac`。OpenSpec 分别使用 `main-market-http-api` 和 `mac-market-http-api` 管理两套接口契约，避免把协议边界和资源边界混合。

备选方案：提供接受 `gotdx` 方法名和参数的通用接口。该方案可能意外暴露实验性方法，弱化参数校验，并且无法形成稳定的 OpenAPI 契约。

### 优先使用 gotdx 高阶方法，仅在稳定能力未覆盖时使用底层方法

高阶 `Stock*` 和 `MAC*` 调用能够提供标准化数据并减少协议细节泄露。财务、公司行为和服务器信息等缺少高阶接口的业务能力使用稳定的底层方法。文件、商品、扩展市场及原始或实验性方法在 API 边界被拒绝。

备选方案：逐一暴露全部底层方法。该方案可以保留协议细节，但会迫使使用者自行标准化数据，并产生不一致的 API。

### 使用受管理的客户端池和有界故障转移

根据配置的主机池创建主市场和 MAC 主市场连接适配器，不创建扩展市场连接。每个适配器依据 `gotdx` 的实际连接行为控制安全并发，通过小型连接池或单连接串行访问避免共享不安全的协议流。仅重试在获得有效响应前失败的只读请求，限制尝试次数，替换损坏连接，并避免隐藏的无限重试。

备选方案：为每个 HTTP 请求创建并断开客户端。该方案简化了所有权，但增加 TCP 建连延迟和上游负载。

### 在 HTTP 边界统一响应与错误

成功响应包含 `data` 以及可选的分页或上游元数据。错误响应包含稳定错误码、消息、请求 ID 和可选字段详情。参数校验失败映射为 400；仅在可明确区分缺失时将上游无数据映射为 404；超时映射为 504；上游不可用映射为 502/503；意外失败映射为 500。

备选方案：直接序列化 `gotdx` 错误。该方案会泄露实现细节，并使客户端依赖不稳定的错误文本。

### 从路由注解生成 OpenAPI 并校验覆盖范围

使用兼容 Swagger 的注解生成 OpenAPI，并由应用提供文档访问。测试对比已注册的稳定路由和文档中的操作。生成文件提交到仓库，使运行时镜像无需生成工具也能提供文档。

备选方案：手工维护 OpenAPI 文档。考虑接口数量较多，该方案更容易与处理器 DTO 发生偏差。

### 集中应用可配置 CORS

在注册路由前安装 CORS 中间件。默认允许所有来源但不允许凭据；配置来源白名单后可用于更严格的部署。服务不得同时使用通配符来源和凭据请求。

备选方案：在各处理器中硬编码通配符响应头。集中式中间件可以正确处理预检请求，并避免路由间行为不一致。

### 构建静态非 root 容器并使用 Compose 编排

使用固定版本的 Go 1.26+ 构建镜像，以面向可重复构建的参数编译，并将二进制、必要证书和 OpenAPI 资源复制到以非 root 用户运行的最小镜像。Compose 负责构建镜像、发布端口、配置重启及停止宽限行为，并执行 HTTP 就绪检查。

备选方案：直接在完整 Go 镜像中运行应用。该方案便于开发，但会增加镜像体积和运行时攻击面。

## 风险与权衡

- [上游项目或 Go 1.26 镜像可能在实施前发生变化] -> 固定经过验证的 `gotdx` 版本和可用 Go 工具链镜像，并在项目文档中记录二者。
- [TDX 协议连接可能不支持并发调用] -> 按连接隔离调用，并通过竞态测试和可控适配器测试验证并发行为。
- [“全部股票相关能力”会形成较大的路由范围] -> 在覆盖矩阵中追踪每个稳定方法，并按共享校验逻辑的相关接口组逐步实现。
- [第三方主机可能缓慢、不可用或返回不一致] -> 使用可配置期限、有界故障转移、请求 ID、就绪诊断，且不得无限重试。
- [默认宽松 CORS 可能允许浏览器直接使用 API] -> 默认不允许凭据，记录配置方式，并支持明确的来源白名单。
- [大型时序响应可能消耗大量内存] -> 限制请求数量和响应规模。
- [生成的 API 文档可能发生偏差] -> 增加自动化路由覆盖和生成一致性检查。

## 迁移计划

1. 新增 Go 模块、应用骨架、配置校验和健康检查接口。
2. 逐步增加上游适配器和接口组，同时保持公共路由前缀为 `/api/v1`。
3. 生成并校验 OpenAPI 文档，然后执行单元测试、竞态测试、集成测试和容器冒烟测试。
4. 使用 Docker Compose 构建并启动服务，验证就绪状态以及代表性的沪深主市场、F10 和 MAC 请求，再发布固定版本镜像。

回滚方式为停止 Compose 服务或重新部署之前的镜像标签。本变更不引入持久化数据或数据库结构迁移。
